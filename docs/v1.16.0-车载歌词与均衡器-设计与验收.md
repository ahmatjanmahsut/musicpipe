## 一、需求 1：蓝牙连接 Mazda 车机时，车机端显示同步歌词

### 1.1 先讲清楚协议事实（决定了实现方式）

蓝牙 AVRCP（Audio/Video Remote Control Profile）**没有"歌词"这个字段**。
车机播放页上能出现的所有文字，都来自手机推过去的媒体元数据三行：

| AVRCP 属性 | Android 侧来源 | 车机典型显示位置 |
|---|---|---|
| TITLE | `MediaMetadata.title` | 第一行（大字） |
| ARTIST | `MediaMetadata.artist` | 第二行 |
| ALBUM | `MediaMetadata.albumTitle` | 第三行 / 详情页 |

而 Android 蓝牙栈取这三行的来源是 **MediaSession 的当前元数据**。
所以在系统能力范围内，"车机显示歌词"只有一条路：
**把"当前歌词行"写进这三行中的某一行**，随播放进度不断更新。

这正是国内音乐 App「车载歌词」功能的做法，也是本版本的实现方式。

### 1.2 实现结构

| 文件 | 职责 |
|---|---|
| `media/car/CarLyricsPlayer.kt` | `ForwardingPlayer` 包装层，覆写 `getMediaMetadata()` 注入歌词行；自己维护监听器名单，在注入文本变化时主动派发 `onMediaMetadataChanged` |
| `media/car/CarLyricsEngine.kt` | 每 200ms 采样播放位置 → 当前歌词行（只在"行变了"时推送） |
| `media/car/CarLyricCursor` + `CarLyricsFormatter` | 纯逻辑：位置→行（含延迟补偿）、行→三字段（含截断/布局） |
| `media/car/OutputDeviceMonitor.kt` | 用 `AudioManager` 输出设备表判断"现在是不是走蓝牙车机" |
| `media/car/CarAudioBus.kt` | 服务 → UI 的单向广播（设置页实时预览"车机会显示什么"） |
| `service/PlaybackService.kt` | MediaSession 面向包装层；启动引擎；设置变化时按新布局重推 |
| `ui/car/CarLyricsScreen.kt` | 设置页：模式 / 写哪一行 / 延迟补偿 / 单行字数 / 实时预览 |

关键点（都在代码注释里写了一遍）：

1. **不改 MediaItem**，只包一层 `ForwardingPlayer`：改 MediaItem 会触发曲目变更事件，
   会被 App 自己的"切歌写历史"逻辑误判成换了一首歌。
2. **自己补元数据事件**：Media3 的 `ForwardingPlayer` 把监听器转给被包装的播放器，
   覆写 `getMediaMetadata()` 本身不会产生任何通知 —— 不补这一下，MediaSession 永远不会把新行推给蓝牙栈。
3. **按行推送而不是每帧推送**：车机端 AVRCP 更新有节流，频繁推会让部分头单元刷屏/闪烁。
4. **没有歌词时推 null**，车机继续显示真实歌名/歌手。车机是用户唯一的屏幕，
   显示"暂无歌词"等于把歌名弄丢。
5. **延迟补偿**（默认 +250ms）：A2DP 从手机到车机出声通常 150~400ms 延迟，
   歌词要"早一点到"才能对上耳朵听到的那句。设置页可 -1000~+1000ms 调。

### 1.3 三种字段布局（为什么必须给用户选）

不同车机播放页读的字段不一样，无法在通用实现里一刀切：

- **标题行**（默认）：歌词占标题，歌名拼到歌手行（"歌名 · 歌手"）。兼容性最好 —— 任何车机都画标题。
- **歌手行**：标题保留歌名，歌词占歌手行。
- **专辑行**：两行都不动，歌词占专辑行（手机通知栏最干净）。

设置页里给了「车机预计显示」的实时预览（用当前真实状态 + 示例歌名渲染三行），
用户在车里对照一次就能定下来。

### 1.4 车机识别

`OutputDeviceMonitor` 用 `AudioManager.getDevices(GET_DEVICES_OUTPUTS)`：

- **不需要任何蓝牙权限**（不会弹用户看不懂的授权框）；
- 名字来自 HAL 的 `AudioDeviceInfo.productName`，车机通常是 `Mazda` / `MZD Connect`；
- 关键词表覆盖 Mazda/mzd/cmu 与常见车厂名、中文"车机/车载"，见 `AudioOutputClassifier`；
- 判不出来时不猜：落到 `BT_OTHER`，用户可把模式切「始终开启」兜底。**默认模式 = 自动。**

### 1.5 已知副作用（已写进设置页说明）

歌词行是**通过媒体元数据**送出去的，所以开启期间手机的通知栏 / 锁屏也会显示这行歌词
（它们读的是同一份元数据）。不希望这样时，把「歌词写进哪一行」改成**专辑行**。

## 二、需求 2：EQ 调节 + 内置预设 + 自定义保存

### 2.1 技术路线

用系统 API `android.media.audiofx.Equalizer`（+ `LoudnessEnhancer` 做增益补偿），
挂在 ExoPlayer 的音频会话上：

- 声音在**手机内**就被调过，再经 A2DP / 耳机送出 ——
  所以车载与耳机预设**不需要车机或耳机支持 EQ**，它们只是"这类输出常见缺陷的补偿曲线"。
- 为了让效果器能在服务创建时就挂上，`PlaybackService` 用
  `AudioManager.generateAudioSessionId()` 自己生成会话 id 交给 ExoPlayer
  （默认要等音频输出初始化才有 id，那样用户点开关时会有一段"没反应"）。

分层（重要，别混）：

```
UI(EqScreen) → EqRepository(用户意图/推荐) → EqController(记住设置+会话) → EqualizerEngine(Android API)
                        ↑ DataStore(PrefsRepository)
```

- **纯逻辑层**（`media/eq/EqModel.kt`、`EqPreset.kt`）：5 段曲线、设备频段重采样、
  编解码。不碰 Android API，所以能在 JVM 单测里跑（`android.media.audiofx` 是桩）。
- 预设曲线一律按**标准 5 段**（60 / 230 / 910 / 3.6k / 14k Hz）书写，
  运行时按设备真实频段做**对数频率线性插值**重采样 —— 换一台 10 段的机器，曲线形状仍然一致。

### 2.2 内置预设

| id | 名称 | 60 | 230 | 910 | 3.6k | 14k | 补偿 | 面向 |
|---|---|---|---|---|---|---|---|---|
| `flat` | 平直 | 0 | 0 | 0 | 0 | 0 | 0 | 基准 |
| `car_mazda` | **Mazda 车机** | -3 | -1.5 | +2 | +3 | -1.5 | +2 | 车机 |
| `car_generic` | 车载通用 | -2.5 | -1 | +1.5 | +2.5 | -1 | +1.5 | 车机 |
| `hp_sony_wh1000xm5` | **SONY WH-1000XM5** | -2 | +0.5 | +1.5 | +2 | +1 | 0 | 耳机 |
| `hp_generic` | 蓝牙耳机通用 | +2 | 0 | +0.5 | +1.5 | +2 | 0 | 耳机 |
| `vocal` | 人声 / 播客 | -4 | -2 | +3 | +3.5 | 0 | +1 | 通用 |
| `bass` | 低频增强 | +6 | +4 | +1 | 0 | -1 | 0 | 通用 |
| `treble` | 高频明亮 | -2 | -1 | 0 | +2 | +4 | 0 | 通用 |

曲线取值的依据（注释里也写了）：

- **Mazda 车机**：车内近场反射多、车门 60~120Hz 有共振、A2DP 压缩削高频 →
  削 60Hz、抬 3.6k 人声清晰度、轻削 14k 毛刺，+2dB 补偿整体响度。
- **XM5**：耳机本身低频偏多、人声略后 → 削一点 60Hz、抬 910~3.6k，14k 只轻抬。
- 这些都是**起始点**，不是唯一答案；用户可微调后另存。

### 2.3 推荐与自动切换

- 状态栏/预设区会按当前输出设备给**建议预设**（识别到 Mazda → 「Mazda 车机」），
  一键应用；
- 另有「跟随输出设备自动切换」开关，**默认关闭**：打开后才会按设备自动切。
  自动改设置是经典雷区（用户会以为"音质突然变了"）。

### 2.4 自定义预设

- 选中任意预设会**顺手打开总开关**（点了"Mazda 车机"却听不出变化，人的第一反应是"功能坏了"）；
- 「把当前曲线存为预设」→ 名称（≤24 字）→ 落盘为 `user_<时间戳>`；
- 自定义预设与内置预设并列显示，可删除；删掉的正是当前选中项时回落「平直」；
- 手动拖滑杆会把 `presetId` 置空（显示"自定义"），避免"名字写着 Mazda 但曲线早被改过"的谎。

### 2.5 手感细节

- 滑杆**拖动中**只推效果器（实时可听），**松手**才写 DataStore。
  一次拖动几十次回调，每次都写盘会让手感明显发涩（见 `EqRepository.previewBand`）。
- 5 段滑杆 + 「补偿」滑杆（0~+12dB）。

## 三、数据存储（DataStore: `musicpipe_prefs`）

| key | 类型 | 含义 |
|---|---|---|
| `eq_enabled` | bool | 均衡器总开关 |
| `eq_preset_id` | string | 当前预设 id（空串 = 用户自定义） |
| `eq_gains` | string | 5 段增益 CSV |
| `eq_makeup_db` | float | 增益补偿 dB |
| `eq_custom_presets` | string | 自定义预设（每行一条，\t 分隔；不用 JSON 库，见 `EqPresetCodec`） |
| `eq_auto_switch` | bool | 跟随设备自动切换 |
| `car_lyrics_mode` | string | `off` / `auto` / `always` |
| `car_lyrics_layout` | string | `title` / `artist` / `album` |
| `car_lyrics_offset` | long | 延迟补偿 ms（-2000~2000） |
| `car_lyrics_max_chars` | long | 单行字数（12~120） |

旧的 3 个 key 与交互全部不受影响；升级上来时取不到新 key 会走默认值（EQ 关、车载歌词自动）。

### 4.2 真机验收（**需要用户在车里跑一次**）

> 这一版的两项功能都无法在 CI 里端到端验证：车机屏幕上的字只能人眼看。

**A. 车机歌词（Mazda）**

1. 手机连车机蓝牙（A2DP），打开 App 播一首有歌词的歌；
2. 设置 → 车载 → 看「当前状态」：输出设备应显示 `蓝牙车机 · Mazda…`，判定为车机 = 是；
   - 若显示"未识别"，把「开启方式」切到**始终开启**；
3. 看车机屏幕：默认「歌词写进哪一行 = 标题行」时，标题行应是当前歌词、第二行是"歌名 · 歌手"；
   - 若车机只显示歌名不显示歌词 → 换成**歌手行**；仍不行 → 换成**专辑行**；
4. 若歌词"比歌声晚" → 把「延迟补偿」往右调（+300~+500ms）直到对上；
5. 若某句太长车机不显示 → 把「单行长度」调小（如 32）。

**B. 均衡器**

1. 播放中进 设置 → 音效 → 开启均衡器；
2. 选「Mazda 车机」（车内）或「SONY WH-1000XM5」（耳机），应立刻听到变化；
3. 拖 3.6k 滑杆 → 人声清晰度变化；松手后退出重进页面，设置仍在；
4. 「把当前曲线存为预设」→ 命名 → 出现在列表里，可切回、可删除；
5. 如果底部出现"本机未能挂上系统均衡器" → 该机型/模拟器不支持 `AudioEffect`（界面上会明确说明，播放不受影响）。

## 五、已知限制（诚实清单）

1. **没有在真实 Mazda 车机上验证过**。字段映射基于 AVRCP 元数据规范与 Mazda Connect
   的常见显示行为；若车机只读专辑行，用户按 §4.2 切换即可。
2. **AVRCP 更新的最小间隔由车机决定**：个别头单元对元数据更新很迟钝（1~2 秒），
   这类车机上歌词会"跳句"而不是逐句滚动 —— 这是协议层限制，不是 App 的 bug。
3. **通知栏/锁屏会同步显示歌词行**（同一份元数据）。可用「专辑行」布局规避。
4. **`AudioEffect` 不是所有机型都有**：模拟器与部分定制 ROM 会创建失败，
   界面会显示明确的原因，EQ 静默不生效，播放与其它功能不受影响。
5. **均衡器只作用于本机输出**：如果用户改用其它 App 播放（或投屏/蓝牙音箱自带 DSP），
   本 App 的曲线不参与。
