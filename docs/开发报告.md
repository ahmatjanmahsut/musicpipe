## 2. 需求覆盖

### R1 登录注册 + 角色权限
- 服务端：register（首用户自动 admin）/login/logout/me；session cookie（HttpOnly, SameSite=Lax, 7 天 TTL）；scrypt 密码哈希；用户 CRUD + 角色分配（admin-only，含 last_admin 保护、不可删自己）。
- Web：登录/注册双 Tab；菜单按 isAdmin 条件渲染；`users/releases` 路由**不静态注册**——admin 登录后 `addRoute`，登出/401 `removeRoute`；普通用户访问落 NotFound（彻底隐藏，非置灰）。
- App：`NavGraphSpec.routesFor(role)` 纯函数决定路由集合；`ADMIN_USERS` 仅 admin 注册 composable；设置页入口 `settingsEntries(role)` admin-only；`RoleNavTest` 5 项断言锁定该行为。

### R2 播放历史本地持久化
- Room `HistoryEntity`（播放即插入，去重置顶）；历史页支持列表/单删/清空（确认对话框）/点击重播；重启不丢（本地数据库）。

### R3 网络歌词 + 同步滚动
- `LyricsRepository`：先 Subsonic `getLyrics`，无则查 MusicPipe `/api/lyrics?platform&songId`、`/api/lyrics/search`；`LrcParser` 支持多时间标签/1-3 位小数/offset 元标签（7 项单测）。
- 歌词页二分查找活动行（`activeIndex`）+ `animateScrollToItem` 滚动 + 当前行高亮放大；未匹配降级为提示条「未匹配到歌词，播放不受影响」。

### R4 收藏「我喜欢」
- Room `FavoriteEntity` 本地持久化；播放页 ♥ 一键收藏/取消（StateFlow 实时联动）；「我喜欢」Tab 离线可看、可取消、可播放（进入队列）。

### R5 APK 更新服务
- Web 管理员上传：multipart ≤200MB，`.apk` 前后端双校验，流式计算 MD5/size，versionCode 重复 409。
- App 链路：检查 `GET /api/app/update/latest` → `VersionUtil.needsUpdate`（versionCode 严格大于）→ OkHttp 下载（进度回调）→ `Md5.file` 校验（失败可重试）→ `canRequestPackageInstalls` 检查 → 引导「未知应用安装权限」→ FileProvider `ACTION_VIEW` 安装；版本一致提示「当前已是最新版本」；下载/校验失败均给「重试」且旧版本可用。
- 下载响应带 `X-Apk-Md5` 头（冒烟已验证与文件实际 MD5 一致）。

## 6. 已知限制与注意事项
- **用户机器注册表 PATH 损坏**：`HKCU\Environment` PATH 末条为 `C:\WINDOWS\System32\OpenSSH" /f`（含多余引号+/f）。会导致 Gradle 测试 worker 启动失败等诡异问题（本项目已用构建前净化 PATH 规避）。建议手工修正为 `C:\WINDOWS\System32\OpenSSH\`。
- harness 内 `pnpm run` 偶发 ELIFECYCLE -4058：server/web 构建改用 `node tsc`/直调 vite 正常；正常终端不受影响。
- mock Subsonic 仅实现 t/s 明文签名参数（契约未要求 p=enc:）。
- Web 主 chunk 1.11MB（Element Plus 全量引入，仅构建警告；瘦身需追加 unplugin 依赖，未引入）。
- App 默认服务器地址 `http://192.168.1.10:7800` / Navidrome `http://192.168.1.10:4533`（可在设置页修改，DataStore 持久化）。
- **验收环境无模拟器/真机**（硬件加速不可用且无管理员权限，详见 §3.3）：App 端未做运行时点测；APK 已构建成功，逻辑经 17 项单测 + 独立评审覆盖。
- mock Subsonic 运行在独立端口 `PORT_SUB=4533`（主服务 :7800 不代理 `/rest/*`）——与真实部署形态一致（Navidrome 本就是独立服务）。
- App `SubsonicApi.getRandomSongs` 发送 `count` 参数，真实 Subsonic/Navidrome 协议参数名为 `size`（服务端忽略未知参数走默认值，行为无差异；建议后续统一为 `size`）。

- 验收使用的测试账号（boss/alice 等）与测试发布（vc1/vc2/vc888 假 APK）**已在交接时全部清空**（`server/reset-for-handover.cjs`）：首个注册用户将自动成为 admin，请部署后第一时间注册自己的管理员账号。

### 12.1 需求 1:App 与后端"连接太慢"的根因诊断

| 路径 | DNS | TCP | TLS | TTFB | 总耗时 |
|---|---|---|---|---|---|
| WAN https://music.example.com | 20ms | 21ms | 34ms | 36ms | 36ms |
| LAN http://192.168.1.10:7800 | — | — | — | — | library 3-5ms |

TLS 首握 19ms、复用后 4ms(TLSv1.3);并发 5 个请求总计 8ms。**WAN 与 LAN 几乎一样快(library 7ms vs 4ms)**,链路不是瓶颈。

| 端点 | 耗时 | 体积 | 结论 |

### 12.2 修复 A:服务端歌词"一次付费,永久 2ms"

在 `src/gateway.js` 增加三级缓存,顺序为 **内存 LRU → tracks.extra 持久化 → 网盘侧车/Navidrome 并发**:

- `lrcFromDb(track)`:读 `tracks.extra` 的 `lrc` 字段。**不改表结构**——`tracks.extra` 本来就是 JSON 文本列,加个键即可。
- `lrcPersist(trackId, text)`:算完写回 `tracks.extra`。
- 内存 LRU 500 条,正结果 TTL 1 小时、空结果 5 分钟(避免"没写歌词"的曲目反复回源)。
- 每级 `withTimeout(LRC_TIER_MS = 8000)` 截断(WebDAV 客户端自带 120s maxExecutionTime,不截断会挂死)。

**后台预热 `lrcPrewarm()`**:启动后延迟 30s,串行扫全库(`remote_path` 非空且 status <> 'failed'),逐首 `lrcText()` 并持久化,每首间隔 400ms。**串行 + 间隔是为了不把网盘 API 打爆、不与下载任务抢带宽**。可用 `settings.lyrics_prewarm=0` 关闭。

首次实测 `done=0`——因为 `tracks.status` 的真实取值是 **`imported`(65)/`uploaded`(3)**,不是早期分享查询里看到的 done/exists。改用 `remote_path` 过滤后正常。同时把"确实没有歌词"标记为 `extra.lrcNone=1`,与"还没抓过"区分开,避免下次预热重复劳动。

**预热结果:`done=68 hit=62 miss=3`**——68 首全部处理,62 首抓到歌词并持久化,3 首确无歌词已打标。

### 12.3 修复 B:App 共享连接池 + Coil 接入

`data/remote/ApiClientFactory.kt` 重写:

```kotlin
private val connectionPool = ConnectionPool(8, 5, TimeUnit.MINUTES)
val sharedClient: OkHttpClient by lazy {
    OkHttpClient.Builder()
        .addInterceptor(DynamicBaseInterceptor { ServerConfig.restBaseUrl })
        .addInterceptor(TokenInterceptor { prefs.authTokenNow() })
```

### 12.7 已知限制(v1.5.0)

1. **歌词冷路径无法根治**:123pan WebDAV 的 `getFileContents` 本身要 418-706ms,属于上游固定延迟,代码层面压不下来。本版的做法是"每首只付一次"(持久化 + 预热)。**新下载的歌在下一次预热前仍会走一次冷路径**。
2. **预热是启动后 30s 的一次性全量扫描**,不是监听新下载。若某段时间大量导入,需重启容器或等下次启动才预热新歌。
3. **"确实没有歌词"的曲目 5 分钟后会重新回源一次**(负缓存 TTL);已打 `lrcNone` 标记的不会再被预热重复抓,但手动点进歌词页仍会重试一次,以便用户补了 .lrc 后能生效。
4. **本地无缓存磁盘**:App 侧歌词缓存只在内存(LRU 500),杀进程后清空。
5. 网速测试需要曲库非空(要有歌可抽样);曲库为空时只测延迟。
6. **主页掉帧是从结构上消除的(重组范围 O(500)→O(可见卡片)),但没有做真机 profiler 验证**——无真机/模拟器环境,流畅度只能从代码结构举证。

### 12.8 复盘:测速复测中的一个测量陷阱(勿被误导)

v1.5.0 发布后做独立复测时,发现 `curl -o /dev/null -w "%{size_download}"` 对 2MB Range 请求稳定报 **523,468/523,469 字节**(3 次几乎同一数值),而同一请求写到真实文件时 `wc -c` 得到 **2,097,152 字节**、8MB Range 请求文件大小为 **8,388,608**。

**结论:这是 curl 把响应写向 `/dev/null` 时的统计假象,不是服务端截断,也不是带宽不足。** 判定依据:截断位置每次几乎完全相同(字节级固定),与网络抖动无关;换成真实文件立即满额。

因此本报告中所有带宽相关结论以**写入真实文件后的实际字节数**为准。App 侧的 `NetBench.measureSpeed` 不依赖 `%{size_download}`,而是自己用 okio `Buffer` 读满 `limitBytes` 才停表,不受该陷阱影响。

#### 13.1.2 补充：被击穿的 lambda 稳定性（本轮新发现）

在核对 strong skipping 模型时发现 HomeScreen 里还有一处会**抵消上述所有优化**的问题：

```kotlin
FolderGrid(
    ...
    onOpenFolder = { id -> vm.openFolder(id) },   // ← 每次重组新建
)
```

lambda 参数在 strong skipping 下按 `===` 比较。写在实参位置的 lambda 每次重组都会新建一个实例，
新旧永不相等 → **每次 UiState 变化（管理态切换、loading 置位、歌单选中变化）整个网格连同全部可见卡片
都会重组一遍**。这不只是滚动问题，任何一次状态抖动都会引发整屏重组。

已改为 `val onOpenFolder: (String) -> Unit = remember(vm) { { id -> vm.openFolder(id) } }`。
详情页的 `onPlay` / `onPlayAll` 同理，按 `remember(vm, folderId)` 固定。

同时修正了两处与注释不符的地方（注释承诺、代码未做）：
- 注释写"卡片额外用 graphicsLayer 提升为独立渲染层"，但代码里没有 `graphicsLayer` → 已删掉该说法，
  改为与实现一致的说明（封面格 `aspectRatio(1f)` 固定高度，滚动中不重复测量）。

**这一轮的处理原则**：注释里写的每一条都回到代码里核实，不成立的删掉，成立的保留。
报告里的"已优化"必须能在代码里指到行号。

### 13.2 连续下载闪退:根因是绕过限流的单请求轰炸

`NetSearchViewModel.downloadAll()` 旧实现把 **4 平台 × 20 首 = 80 首**全塞进一个 POST:
- 不走 `enqueueSlots`(Semaphore(3)) ,也不分批 → 请求体数百 KB,序列化+网络同时冲高;
- 任一异常整批放弃。

改为按 **10 首一片**分片入队,每片独占一个并发槽、片间 `yield()`,逐片容错统计成功/失败,
最后 toast「已加入 N 首,失败 M 首(可稍后重试)」;入队期间按钮禁用防连点。

### 13.3 "文件头(mp3)与扩展名(flac)不符":真正的机制

**这不是文件损坏,而是请求了曲目不存在的音质。** 实测(曲目「顺流逆流」kw,songmid 211909578,该曲目只有 128k):

| 请求方式 | 结果 |
|---|---|
| 直接请求音源 `format=flac` | 返回纯文本 `refuse request!` |
| 走服务端管线 `quality=flac` | 落盘文件前 12 字节 = `162e0f2637634d4c52645465` —— 既不是音频也不是那段文本,是兜底返回的加密/压缩流 → 必然校验失败 |
| 走服务端管线 `quality=128k`(与曲目能力相符) | 正常完成,`顺流逆流.mp3` 3,834,555B |

修复分两层:
1. **服务端加音质嗅探**(v1.6.0 新增):`adapter.js` 加 `sniffAudioType(url)`(Range 取前 2KB)+ 纯函数 `sniffBuffer()`(fLaC/ID3/OggS/RIFF/ftyp/0xFF-E0);`runner.js` 在推导扩展名前先嗅探,**能识别真实格式就按真实格式纠正 ext+quality**(并记 `quality_override` 事件),识别不出就交给 `checkMagic` 判失败 —— 垃圾永远不会进曲库。
2. **报错必须可操作**(本轮补上):原来只抛「校验失败: 无法识别的音频文件头」,用户只会反复重试。现在嗅探+checkMagic 双双判非音频时,直接抛
   **「该曲目没有 flac 音质的资源,请把音质改成「自动」或 128kbps 后重试」**,并记 `quality_unavailable` 事件;
   其它校验失败也附带「(请把音质改成「自动」或更低音质后重试)」。
3. **App 侧翻译兜底**:新增纯函数 `GatewayUtil.humanizeTaskError()`,把服务端错误码翻成人话(音质不符 → 建议改自动/128k;试听片段 → 换平台;取链失败 → 版权或链接过期;网盘 → 去 Web 控制台检查),任务列表失败项直接展示翻译后文案并标红。

**部署位置曾经踩坑**:嗅探最初写进了 `.tmp/router-live/` 下的扁平旧副本(那里不是容器真正运行的文件,
容器跑的是 `src/sources/adapter.js` 与 `src/downloader/runner.js`),改了完全不生效。已按正确路径重新部署并验证。

|---|---|---|

## 15. v1.8.0（vc9）—— 冷启动白屏排查与修复

### 15.1 现象

用户反馈：冷启动后白屏时间很长。

先明确"白屏"到底是什么。冷启动的显示顺序是：

```
点图标 → [系统窗口背景] → [首帧：Compose Surface] → [数据就绪：真正内容]
          ↑ 主题 windowBackground        ↑ LoadingBlock 画的空白+小转圈
```

对本 App 而言，"白屏"实际上是**第二段**：`LoadingBlock` 只在正中间画一个小红圈，
整屏底色就是 `Surface` 的 background（浅色主题下 #F9F9F9），远看就是一片白。
所以问题不是"首帧画不出来"，而是**首帧之后停留在 LoadingBlock 上的时间太长**。

### 15.2 根因（按影响排序）

#### 根因 1：首屏在等网络往返（决定性）

`MusicPipeApp.kt` 原来的门是这样写的：

```kotlin
var restored by remember { mutableStateOf(false) }
LaunchedEffect(Unit) {
    container.authRepository.restoreSession()
    restored = true          // ← 只在 restoreSession() 全部返回后才置 true
}
when {
    !restored -> LoadingBlock(...)   // 一直在转圈
    ...
}
```

而 `AuthRepository.restoreSession()` 内部第一步就走 `api.me()` 网络请求。
OkHttp 的 read 超时配的是 **30 秒**。于是：

- 局域网正常时：多等 100~500ms；
- **网络慢、Wi-Fi 未连、或路由器不可达时：一直等到超时，最长 30 秒**。

v1.7.0 虽然已经改成"先设缓存身份再请求 /me"，但那个 `restored` 标志位仍然
绑在**整个 restoreSession 返回**上 —— 本地身份早就有了，UI 却还在等网络。
**这是一个自相矛盾的写法：数据层抢先了，UI 层又把优势抵消掉了。**

#### 根因 2：窗口背景是接近白色的固定值

`res/values/themes.xml` 里：

```xml
<item name="android:windowBackground">@color/windowBackground</item>
```
```xml
<color name="windowBackground">#F9F9F9</color>
```

值本身和浅色主题一致（没错），但**没有 night 版本**。系统处于暗色模式时，
Compose 一上来就是深色底，而这层窗口背景仍是 #F9F9F9 → 先闪一下白再变黑。
`statusBarColor` 也是硬编码 `#FFFFFF`，暗色下会先出现一条白状态栏。

#### 根因 3：启动主线程上额外创建了 ExoPlayer

`AppContainer.init` 里有一句：

```kotlin
appScope.launch { playerController.connect() }
```

`appScope` 是 `Dispatchers.Main.immediate`，而 AppContainer 是在
`MainActivity.onCreate` 里、**setContent 之前**构造的 —— 所以这个 launch 会立刻在主线程
同步跑到第一个挂起点，发起 MediaController 绑定 → 拉起 `PlaybackService.onCreate` →
**创建 ExoPlayer**（含音频属性、MediaSession，冷启动时是主线程上最贵的一步）。
而启动阶段根本没有播放需求，这笔开销纯属白付。

> 另外确认：`LoadingBlock` 自身很轻（一个 Box + CircularProgressIndicator），
> 不是耗时来源；`AppContainer` 里的 Room/Retrofit 构造会占几十毫秒，但远不是秒级。

### 15.3 修复

| # | 改动 | 文件 |
|---|---|---|
| 1 | 把"决定首屏去向"和"网络校正"拆开：本地一有结论立刻置 `restoreReady`，`/me` 只用于事后校正 | `data/repo/AuthRepository.kt` |
| 2 | 放行规则抽成纯函数 `StartupGate.canShowUiWithoutNetwork(hasToken, hasCachedIdentity)` 并加单测 | `data/repo/StartupGate.kt`、`StartupGateTest.kt` |
| 3 | UI 的门改看 `restoreReady`，不再看"restoreSession 是否返回" | `ui/MusicPipeApp.kt` |
| 4 | `windowBackground`/`statusBarColor` 改为跟随明暗主题（新增 `values-night`） | `res/values{,-night}/colors.xml`、`themes.xml` |
| 5 | MediaController 绑定推迟到首帧之后（`OnPreDrawListener` 首次回调时触发） | `MainActivity.kt`、`di/AppContainer.kt` |
| 6 | 启动耗时可测量：`AppContainer ready in Xms`、`restoreReady (usable UI) in Xms`、`reportFullyDrawn()` | `MainActivity.kt` |

**修复后的启动时序**：

```
系统窗口背景（已跟随明暗主题，不再是白的）
  → 首帧 Compose Surface
  → DataStore 读本地身份（几十毫秒）→ restoreReady = true → 主界面
  → 之后：/me 后台校正、ExoPlayer 绑定、曲库刷新
```

关键点：**首屏只依赖"读本地磁盘"，不再依赖任何网络往返。**
只有一种情况仍要等网络：本地有 token 但**没有**缓存身份（无法判断角色、无法构建导航图），
这属于升级后首次启动的极端边界，此时等待是不可避免的。

#### 顺带修掉的一个隐患

推迟绑定引入了新的窗口期：用户可能在控制器连上之前就点了播放。
原来的 `playQueue` 是 `val mc = controller ?: return` —— **会把这次点击悄悄吞掉**。
现在改为 `pendingAction` 暂存，控制器连上后立刻补执行（`MusicPlayerController.withController`）。
不修这个，性能优化就会变成一个"偶发点了没反应"的 bug。

### 15.5 已知限制

1. **显式主题与系统主题不一致时仍有一次闪变**：App 支持"强制浅色/强制深色"，

3. **未引入启动主题（Splash Screen）**：本次只做了"不白 + 不等网络"，
   没有做 Android 12+ 的官方启动画面。若要品牌化的启动动画，可后续加 `core-splashscreen`。

## 16. v1.9.0（vc10）：主页「歌单 / 专辑」重复修复

> 用户反馈（原文）：「主页中显示的专辑和歌曲是同一个分享链接导入的，重复了，你找一找其他音乐类app是怎么实现的然后优化主页，防止重复」

### 16.1 现象与真实数据

线上探针（router 容器内 node:sqlite 直读 `/data/config/musicpipe.db`）结果：

| 查询 | 结果 |
| --- | --- |
| sharelinks | `[{"id":"mvfdec9j7d0eadfd9d47","title":"ahmattjon喜欢的音乐","song_count":104}]`（全库仅 1 个歌单） |
| tracks 总数 | **101** |
| 按 album 分组 | `{"ahmattjon":101}` —— **101 首的 album 全部等于分享者昵称** |
| sharelink_items | 104 行，其中带 track_id 101 行，已入库 101 行 |

也就是说：曲库 101 首 100% 来自这 1 个歌单，且它们的 album 字段全被写成 `ahmattjon`。App 首页把「分享歌单」与「专辑」两个维度铺在同一个网格里，于是出现了 2 张内容完全相同的卡片 —— 用户看到的"重复"是**两个维度的同源数据同屏**，不是重复插入。

### 16.2 两个根因

**根因 A（App）**：首页网格把 `build(songs, collections)` 的返回（分享 + 专辑 + 未分类 三种文件夹混排）直接铺开，同一屏必然出现"歌单卡片"和"它的专辑卡片"。

**根因 B（服务端，决定性的数据错误）**：

`src/pipeline/sharelink.js` 旧代码
```js
function pickShareUser(link) {
  var by = String(cfg("share_album_by", "user"));
  return by === "playlist" ? (link.title || "分享歌单") : (link.share_user || link.title || "分享歌单");
}
// :204 与 :247
var share = { folder: folder, album: folder, no: it.no, link_id: id, playlist: link.title };
```
`src/downloader/runner.js` 旧代码无条件覆盖：
```js
if (share && share.album) {
  meta.album = share.album;
  meta.albumArtist = share.folder || share.album;
  meta.trackNumber = String(share.no || "");
}
```
即 `album = folder = 分享者昵称`，把每首歌的**真实专辑名丢掉了**。真实专辑名其实一直拿得到（`sharelink.js:97-103` 从网易云 song/detail 取 `al.name` 并写入 song_json），只是被这个覆盖盖掉了。

### 16.3 同类 App 的做法（调研结论）

| App | 结构 |
| --- | --- |
| Apple Music | 资料库下 播放列表 / 艺术家 / 专辑 / 歌曲 是**四个独立入口** |
| Spotify | 首页分轴 carousel；资料库是独立 tab |
| Navidrome | 首页多个横向 carousel（最近添加 / 专辑 / 播放列表），每个 carousel 一个维度 |
| DsoMusic | 歌曲 / 专辑 / 艺术家 / 歌单 **分 tab** |

共同点：**一次只展示一个维度**。没有任何一个把"歌单"和"它的专辑"并排铺在同一屏。据此，v1.9.0 采用"拆轴"而不是"过滤掉重复"。

## §17 封面空白事故（v1.9.1 服务端热修）

用户反馈（2026-10-20）："曲库还有很多音乐封面是空白的"。

### 17.1 现象与排查起点

App 曲库 101 首中大量封面为白图。App 侧的封面链路是 `FadeInCover`（Coil）请求 `GET /api/v1/cover/:id`；该端点有两级来源：

1. **网盘同名 `.jpg` sidecar**（与歌词 `.lrc` 同样的存储方式，命中优先，内存缓存 10 分钟）；
2. **Navidrome 内嵌封面**（`search3` 取 `coverArt` 再取图，回退链路）。

两级都空时返回 `404 {"error":"无封面"}` —— App 显示占位底色，就是用户看到的"空白"。

### 17.2 根因 1：v1.6.0 部署用陈旧副本覆盖了 runner.js，封面抓取整段丢失（决定性）

这是本次事故的主因，责任在发布流程而非代码设计：

- v1.4.0 时 runner.js 里有完整的封面抓取：`import { fetchCoverBuf }` → 下载时抓 `song.img` → 作为 `coverBuf` 内嵌进标签 → 同时上传同名 `.jpg` sidecar。
- v1.6.0 我为修"音质嗅探"改了 runner.js，但当时使用的本地源码树 `/path/to/musicpipe\.tmp\router\musicpipe\src` 是**陈旧副本**（比线上少 7KB 的 gateway.js、少 routes/appsvc.js、少 downloader/cover.js）。部署后线上 runner.js 变成"有嗅探、无封面"的版本，`coverBuf` 计数从 5 变成 0。
- 后果：此后下载的 101 首既无内嵌封面，也无 sidecar；Navidrome 对无内嵌图的新文件也没有 `coverArt` → 两级全空 → 全白。

**证据（镜像扫描）**：10-19 06:33 构建的镜像（6b51536e6c5c）里 runner.js `coverBuf=5`；10-19 10:26/10:36/10:38 构建的镜像（含我的嗅探补丁）`coverBuf=0` 且 `sniffAudioType=2`。曲库 101 首的 `created_at` 全部晚于 06:33，落在这批"无封面代码"的 runner 之下。

### 17.3 根因 2：kw / kg / tx 平台搜索结果的 `img` 恒为 null

`src/sources/search.js` 里只有网易云（wy）映射了 `img = item.al.picUrl`；kw（:96）、kg（:96/100）、tx 的映射写死 `img: null`。因此**即使封面代码正常**，这些平台的歌也永远抓不到封面。App 的"网络搜索 → 下载"大量走 kw，所以这部分空白与根因 1 无关。

### 17.4 修复（服务端四项，全部已部署）

| # | 改动 | 文件 |
|---|---|---|
| 1 | 以**运行中镜像**（a55154e57bcc，10-19 10:38）为准重建本地源码树，丢弃陈旧副本 | `docker create + docker cp <cid>:/app/src` |
| 2 | 恢复封面抓取（`fetchCoverBuf` import / `coverBuf` 抓取 / `tagMeta` 内嵌 / `.jpg` sidecar 上传），保留 v1.6.0 嗅探与 v1.9.0 album 补丁 | `src/downloader/runner.js` |
| 3 | 新增在线封面反查 `lookupCoverUrl(title, artist)`：只在歌名归一化完全相等、且歌手也一致时采用（歌手为"未知歌手"时退化为仅歌名匹配）；查不到返回 null | `src/downloader/coverlookup.js`（新增） |
| 4 | `GET /api/v1/cover/:id` 增加第三级"自愈"：sidecar 与 Navidrome 都空时在线反查 → 抓到即**写成 sidecar** 并回给这次请求，下次直接命中 | `src/gateway.js` |

runner 侧接入方式：`var coverSrc = song.img || ""` 为空时 `coverSrc = await lookupCoverUrl(song.name, song.artist || song.singer)`，再 `fetchCoverBuf(coverSrc)`；同一份 `coverBuf` 同时用于内嵌标签与 sidecar，不重复下载。

### 17.5 存量回填：101 首全部补齐

用 `sharelink_items.song_json` 里的 `img`（wy 的 picUrl）反查曲目，逐首写入 `<remote_path 去扩展名>.jpg` sidecar：

```

```

（`skip=3` 是早已存在 sidecar 的曲目，未重复上传；`noimg=0` 说明 101 首都能在分享条目里找到图片地址。）

### 17.7 已知限制

1. **"未知歌手"的曲目只能按歌名匹配**，同名不同版本（翻唱/现场/纯音乐）可能贴到别的版本封面。这比留白更"看起来正常"，但严格说是近似。若能补到歌手的曲目则不存在该问题。
2. 自愈只在**有人请求**该曲目封面时触发（懒加载），不是后台批量任务；因此打开某首从未展示过的老歌时，第一次可能略慢（多一次反查 + 一次图片下载，实测 <1s）。
3. App 无需发版：本次全部为服务端改动，App 只需重新拉一次曲库（下拉刷新或重进首页）即可看到封面。

### 17.8 流程教训（已写入路由器整合报告）

**任何服务端改动前，必须先把运行中镜像的 `/app/src` 导出为基线**（`docker create <img> && docker cp <cid>:/app/src`），再在其上改动。项目本地源码树此前已多次与线上漂移，本次事故正是"用旧副本覆盖线上新代码"的直接后果 —— 损失的不是代码本身，而是 101 首歌的封面元数据，且只有用户看到才被发现。

### 18.7 已知限制

1. **没有任何一项性能改进有真机帧率数据**。本环境无真机/模拟器，所有结论都来自代码结构（谁在滚动帧内计算、谁必然无法跳过重组、谁每 500ms 触发）。P1/P2/P3/P4 的收益量级需要用户在真机上用 Android Studio Profiler 或 `adb shell dumpsys gfxinfo` 复核。
2. **V4 字体改动会改变现有界面观感**：原来 22 处字号是"照着截图逐处调"的，改走 `Typography` 后个别地方可能与原设计差 1sp。这是一次性对齐成本，换来的是跟随系统字号缩放。
3. **V7 自适应列数改变了横屏/大屏布局**：手机竖屏保持不变（150dp × 2 = 300dp < 常见 360dp 宽），但平板/折叠屏展开会变成 3~4 列，封面拼图密度与原来不同。
4. **C2 改了异常兜底策略**：以前所有 IO 异常都静默，现在只有网络类静默。若有未覆盖的 IO 路径会开始出现崩溃上报 —— 这是**预期行为**（把"假活"暴露成真崩溃），但如果用户看到新的崩溃，请把堆栈发我。
5. **C1 只在登出时清缓存**，同一账号切换服务器地址（设置页改 MusicPipe 服务地址）不会清快照 —— 换服务器后首屏可能先显示旧服务器的曲库。这是既有行为，本轮未改（改它需要处理"半途清空导致页面闪空"的体验问题）。

### 20.4 实现要点

**为什么必须用 `key(appStyle, dark)` 重建子树**：token 现在是普通 getter（读 `StyleState.spec`），不是 snapshot state，Compose 不会因为规格变化而自动重组。`MusicPipeTheme` 在组合子项前 `StyleState.apply(appStyle, dark)`，再用 `key()` 丢弃旧组合按新规格重建 —— 一次性、无残留，语义上也正确（换的是整套设计而非某个值）。

**为什么 `StyleState` 用 `@Volatile` 而不是 snapshot state**：在组合期写 snapshot state 会触发重组循环；而这里写入后本帧立即生效，不需要也不应该再触发一次重组。

**为什么 Shape 要缓存**：`AwwShapes.bundle()` 按 style 缓存 RoundedCornerShape，避免每滚动帧给 30 张卡片各 new 一个 Shape。

**新增 token `onAccent`（必要修复）**：强调色之上的文字原先写死 `AwwColors.Paper`（深色底）。但 Material 深色模式的强调色是浅紫 #D0BCFF、shadcn 的强调色是纯白 #FAFAFA —— 浅底浅字直接看不见。已引入 `onAccent` 并修正 4 处（PlayerScreen.kt:204、ShareImportScreen.kt:198/376、LoginScreen.kt:248）。

**顺带修掉的写死颜色**：`HomeScreen.kt` 管理态未选中标记原用 `Color.Black.copy(alpha=0.35f)`，浅色风格下与深色封面糊在一起；勾选图标原用 `colorScheme.background`，在浅色强调色上是浅底浅勾。已改为 `AwwColors.Ink` 与 `AwwColors.OnAccent`。

**刻意的例外**：`SettingsScreen.kt:395/396/402/403` 的琥珀 #E6A23C 与红 #F56C6C 是延迟/带宽分档的**诊断数据**，不是装饰，不 token 化（代码注释已写明）。

### 21.2 八处根因与修复

按「影响面 × 严重度」排序。序号后标注的是修复所在文件。

#### ① 全局噪点层每帧推进动画 —— 整屏每帧重绘（影响面：全部页面）

`/path/to/musicpipe\app\src\main\java\com\musicpipe\player\ui\design\AwwPrimitives.kt` 的
`GrainOverlay`，通过 `MusicPipeApp.kt:100` 挂在**整棵树最外层**，铺满全屏。

旧实现：

```kotlin
val transition = rememberInfiniteTransition(label = "grain")
val phase by transition.animateFloat(...)          // 无限动画
val step = if (reduceMotion) 0f else floor(phase)  // 在组合体里读值！
Box(modifier.graphicsLayer { translationY = step * 13f })
```

两个独立的错误叠在一起：

1. `by` 委托在**组合阶段**读动画值 → 每帧（60 次/秒）重组一次，
   每次重组都重建整条 Modifier 链与 `drawWithCache` 节点；
2. 即使把读值挪进 `graphicsLayer {}`（draw 阶段），
   `rememberInfiniteTransition` 仍然每帧推进一次动画值，
   于是这个全屏图层每帧都被标记为需要重绘 → GPU 每帧重画一整屏。

它挂在最外层，所以表现是「**不管滑到哪都卡**」，与列表内容无关。

修复：噪点的视觉语义本来就是 CSS `steps(10) 8s`（一秒只跳 1.25 次），
所以直接离散化——`LaunchedEffect` 每 800ms 只更新一次 `Int` 状态，
`graphicsLayer` 内读该整数。重绘从 60 次/秒降到 **1.25 次/秒**，观感完全一致。

#### ② 卡片入场动画在列表回收复用后重播（影响面：主页网格）

`AwwPrimitives.kt` 的 `ClipReveal` / `MaskReveal` 用
`remember { Animatable(0f) }` + 1200ms 动画。

`remember` 的存活期跟着**组合**走，而 `LazyVerticalGrid` 会把滑出屏幕的条目销毁、
滑回来时重新组合 → 动画又从头播一遍。滚动过程中不断有新卡入场，
一屏最多 6 个 `Animatable` 并行推进、逐帧写 `graphicsLayer`。

修复两层：

- `ClipReveal`/`MaskReveal` 增加 `animate: Boolean = true` 参数，
  `false` 时直接从终态（`progress` 初值 1f）开始，**完全不创建动画**；
- `HomeScreen.kt` 的 `FolderCard` 用进程级 `revealedFolders` 集合记录已播过的卡片 id：

```kotlin
private val revealedFolders = java.util.Collections.synchronizedSet(HashSet<String>())
private fun revealOnce(id: String): Boolean = revealedFolders.add(id)
```

入场美感保留**一次**，滚动复用不再反复播。

#### ③ 下载任务列表 O(n²)（影响面：任务页）

`TasksScreen.kt` 旧写法：

```kotlin
items(state.tasks, key = { it.id }) { task ->
    TaskRow(index = state.tasks.indexOf(task) + 1, ...)
}
```

`indexOf` 是线性查找，而它对**每一行**都执行一次 → 整个列表 O(n²)。
更糟的是任务列表在下载进行中因为进度更新**每 500ms 就重组一次**，
50 条任务时每轮要跑 2500 次引用比较。

修复：改 `itemsIndexed`，序号直接来自下标。

#### ④ 历史/收藏列表每帧重建 Song 与带 token 的 URL（影响面：历史页、收藏页）

`HistoryScreen.kt` / `FavoriteScreen.kt` 的行内直接调用
`container.historyRepository.toSong(track)`。该方法内部：

```kotlin
fun toSong(track: HistoryTrack): Song = SongMapper.fromCached(..., token = AuthTokens.get())
```

`fromCached` 会走两遍 `ServerConfig.signed(cover/stream, token)`，
每次都要判前缀、`trimEnd('/')`、拼 `/`、拼 `?token=` —— 3~4 个中间字符串，

## 25. v1.15.0（vc15）：启动「一直转圈」根因与修复

用户诉求原文（2026-10-23）：「每次打开app时中间那个圈就一直在转」。

### 25.1 先说清楚：App 里没有「圈」

全 app 搜索 `drawCircle` / `Canvas(` / `CircleShape` / `drawArc` / `CircularProgressIndicator`，**命中只有 3 处注释**，没有任何圆形绘制代码。用户看到的「中间的圈」是加载组件 LoadingBlock（ui/components/Common.kt）的内容：

```
MUSICPIPE
000            ← 每 1600ms 从 000 走到 099 再重置
————————
```

数字用等宽字体、居中显示，循环跳动时的观感就是一个「一直在转的圈」。这个组件在 v1.12.0 按 DESIGN.md 从 CircularProgressIndicator 改成了计数器——**改掉了圆圈，但保留了「一直在动」，问题因此在观感上被继承下来**。

### 25.2 三个真实根因

**根因 1（决定性）：loading 判断缺一维，「等网络」和「等本地」被混为一谈**

HomeViewModel.refresh() 在发起网络请求**之前**无条件置 `loading = true`；而首屏的可显示内容 `hasContent` 来自曲库，冷启动时必须等网络。于是必然路径是：

```
loading=true 且 hasContent=false  →  命中 HomeScreen 的 loading && !hasContent 分支  →  显示计数器
                                →  一直持续到 GET /api/v1/library 返回为止
```

v1.7.0 引入的本地快照本应抢在网络之前渲染，但快照读取是**另一条协程**（init 里 viewModelScope.launch { cachedLibrary() }），与 refresh() 并发、互不等待。快照比网络快时首屏正常；一旦 Room 冷启动 open + MIGRATION_2_3 变慢（首次安装、或登出后 clearSnapshot() 导致快照为空），计数器就全程停留。网络侧最坏等待时间由 `readTimeout = 120s` 决定（data/remote/ApiClientFactory.kt），不是此前记录的 30s。

**根因 2：每次回到前台都触发一次带指示器的刷新**

HomeScreen 的 `LifecycleResumeEffect` 无条件调 `vm.refresh()`，refresh 又把 loading 置 true，而 PullToRefreshBox 用 `state.loading && hasContent` 当 isRefreshing —— **每次切回 App，顶部都会转一圈下拉刷新指示器**，即使数据是几秒前刚拉的。这是「每次打开都要转一下」的另一半来源。

**根因 3：几十毫秒的加载也会画出计数器**

LoadingBlock 没有延迟门，快路径（快照命中，通常 5~50ms）也会先画一帧 000 再切走，等于闪一下。

| # | 改动 | 文件 |
|---|---|---|
| 1 | 新增 `bootstrapped` 字段：本地快照读完（**无论是否为空**）即置 true；快照有内容时同时把 loading 置回 false | HomeViewModel.kt |
| 2 | 加载判断抽成纯函数 HomeLoadingGate.resolve()，四态：BOOTSTRAPPING / SYNCING_EMPTY / EMPTY / CONTENT | ui/home/HomeLoadingGate.kt（新增） |

### 25.4 一个被推翻的判断（记录以免重犯）

排查中途我曾判断「冷启动 DataStore 被 .first() 读了 5 次、5 次独立读盘」，并打算把它当作修复方向。**这个判断是错的**：DataStore 的 store.data 是同一个 DataStoreImpl 上的单一冷 Flow，内部持有已解码的内存状态——第一次 .first() 才真正解析文件，之后每次只是取内存快照。5 次调用是 5 次协程挂起/恢复，磁盘解析只发生 1 次。收敛它属于无效优化，已从方案中删除。

这个错误值得记下来：**代码里看到 N 次调用，不等于 N 次 IO**。

## 26. v1.16.0（vc16）：车载（蓝牙车机）歌词 + 均衡器

> 用户需求（2026-10-28）：
> ①「通过蓝牙连接 Mazda 车机播放音乐时，车机端不显示歌词，需新增车机端显示歌词的能力，使其可正常同步展示当前播放歌曲的歌词」；
> ②「新增 EQ 调节功能，并内置多个已调好的预设方案，至少包含连接蓝牙车机时优化的预设（如 Mazda 车机）和连接蓝牙耳机时的预设（如 SONY 1000XM5），同时支持用户手动调节并保存自定义设置」。

### 26.1 先确认协议事实（决定了功能①的实现方式）

蓝牙 AVRCP **没有"歌词"字段**。车机播放页上的一切文字都来自手机推过去的媒体元数据三行
（TITLE / ARTIST / ALBUM），而 Android 蓝牙栈取这三行的源头是 MediaSession 的当前元数据。
所以"车机显示歌词"在系统能力范围内只有一条路：**把当前歌词行写进这三行中的某一行并随进度刷新**。
这不是取巧，而是国内音乐 App「车载歌词」的通行做法；同时它决定了三件事必须由用户可配：
写哪一行（车机各自不同）、延迟补偿（A2DP 有 150~400ms 延迟）、单行字数（部分车机对超长行直接不显示）。

### 26.2 功能① 实现要点

| 文件 | 职责 |
| --- | --- |
| `media/car/CarLyricsPlayer.kt` | `ForwardingPlayer` 包一层，覆写 `getMediaMetadata()` 注入歌词行；自留监听器名单并主动派发 `onMediaMetadataChanged` |
| `media/car/CarLyricsEngine.kt` | 每 200ms 采样播放位置 → 当前行，**只在换行时推送** |
| `media/car/CarLyricsFormatter.kt` | 纯逻辑：三种布局映射 + 截断 + 空白折叠；`CarLyricCursor` 负责位置→行（含 offset） |
| `media/car/OutputDeviceMonitor.kt` | `AudioManager` 输出设备表 → 是否走蓝牙车机（**不需要任何蓝牙权限**） |
| `media/car/AudioOutput.kt` | 设备名/类型 → `AudioOutputKind` 分类（纯函数，可单测） |
| `media/car/CarAudioBus.kt` | 服务 → UI 单向广播（设置页实时预览"车机会显示什么"） |
| `service/PlaybackService.kt` | MediaSession 面向包装层；启动引擎；设置变化按新布局立刻重推 |
| `ui/car/CarLyricsScreen.kt` | 设置页：模式 / 字段位置 / 延迟补偿 / 单行字数 / 预览 |

五个关键取舍（都写进了代码注释）：

1. **不改 MediaItem，只包一层 ForwardingPlayer**。`replaceMediaItem` 会触发曲目变更事件，
   而 App 的 `onMediaItemTransition` 正在写播放历史——每换一句歌词就等于"又切了一首歌"。
2. **必须自己补元数据事件**。Media3 的 ForwardingPlayer 把监听器转给被包装的播放器，
   覆写 `getMediaMetadata()` 本身不产生任何通知，不补这一下 MediaSession 永远不会把新行推给蓝牙栈。
3. **按行变化推送**，不是每 tick 推。车机端 AVRCP 更新有节流，频繁推在部分头单元上表现为刷屏/闪烁。
4. **没歌词推 null**，车机继续显示真实歌名/歌手。车机是用户唯一的屏幕，写"暂无歌词"等于把歌名弄丢。
5. **车机识别不猜**。识别不出就落 `BT_OTHER`，用户可切「始终开启」强制推送——比"自以为识别成功"更可控。

默认值：模式=自动（识别到车机才注入）、字段=标题行（兼容性最好，歌名挪到第二行拼成「歌名 · 歌手」）、
延迟补偿=+250ms、单行字数=48。

### 26.3 功能② 实现要点

技术路线：`android.media.audiofx.Equalizer` + `LoudnessEnhancer`（增益补偿），挂在 ExoPlayer 的音频会话上。
声音在**手机内**调好再经 A2DP/耳机送出，所以车载与耳机预设**不依赖车机或耳机本身支持 EQ**。
为了让效果器在服务创建时就能挂上（而不是等音频输出初始化），`PlaybackService` 用
`AudioManager.generateAudioSessionId()` 自己生成会话 id 交给 ExoPlayer。

分层（职责不要混）：

```
EqScreen → EqRepository（用户意图/推荐/落盘） → EqController（记住设置+当前会话） → EqualizerEngine（Android API）
                    ↑ PrefsRepository(DataStore)
```

预设曲线一律按**标准 5 段**（60 / 230 / 910 / 3.6k / 14k Hz）书写，运行时按设备真实频段做
**对数频率线性插值**重采样——换一台 10 段的机器曲线形状不变。这是本版本最容易算错、也最值得回归测试的一块，
因此整层不碰 Android API，可在 JVM 单测里跑。

| id | 名称 | 60 | 230 | 910 | 3.6k | 14k | 补偿 | 面向 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `flat` | 平直 | 0 | 0 | 0 | 0 | 0 | 0 | 基准 |
| `car_mazda` | **Mazda 车机** | -3 | -1.5 | +2 | +3 | -1.5 | +2 | 车机 |
| `car_generic` | 车载通用 | -2.5 | -1 | +1.5 | +2.5 | -1 | +1.5 | 车机 |
| `hp_sony_wh1000xm5` | **SONY WH-1000XM5** | -2 | +0.5 | +1.5 | +2 | +1 | 0 | 耳机 |
| `hp_generic` | 蓝牙耳机通用 | +2 | 0 | +0.5 | +1.5 | +2 | 0 | 耳机 |
| `vocal` | 人声 / 播客 | -4 | -2 | +3 | +3.5 | 0 | +1 | 通用 |
| `bass` | 低频增强 | +6 | +4 | +1 | 0 | -1 | 0 | 通用 |
| `treble` | 高频明亮 | -2 | -1 | 0 | +2 | +4 | 0 | 通用 |

取值的依据是"补偿已知缺陷"：车内近场反射多、车门 60~120Hz 共振、A2DP  Compression 削高频 →
削 60Hz、抬 3.6k；XM5 低频偏多、人声略后 → 削 60Hz、抬 910~3.6k。**这些是起始点，不是唯一答案。**

交互上的三条硬约束：

- **拖动中只推效果器、松手才写 DataStore**。一次拖动几十次回调，每次都落盘会让手感明显发涩。
- **不自动改用户设置**：按输出设备只给「建议预设 + 一键应用」；「跟随设备自动切换」默认关闭。
- **选预设顺手打开总开关**（否则用户点了"Mazda 车机"却听不出变化，会判定功能坏了）；
  手动改滑杆则把 `presetId` 置空显示"自定义"，不让"名字写着 Mazda、曲线早被改过"发生。

### 27.6 已知限制

1. **没有 Lighthouse 分数**：本机没有可用的 Lighthouse 环境，只有上面实测的字节数、对比度与热区；
   Perf/A11y 分数请在浏览器 DevTools 里复核。
2. **概览"磁盘（挂载视图）"显示 1024.00TB / 0%**：这是 rclone FUSE 挂载点上报的容量（1PiB 级伪值），
   不是本次改动引入的；已把它格式化成 TB 以免出现 1048576.00GB 这种噪音，真正想看的容量需要换成宿主 statfs。
3. **浅色模式的层级压缩**：为了让 12px 标签达到 AA，浅色 ink-3 从 0.42 提到 0.62、ink-2 到 0.70，两者差异变小；
   若以后想要更"轻"的次级文字，正确做法是把标签字号提到 13–14px，而不是把对比度降回去。
4. **仍未引入组件库**：组件外观是按 guide 手写的 CSS（约 45KB），不是 shadcn/AntD。
   取舍是同源零构建（老 SPA 无打包器）与"不擅自换技术栈"；将来若引入构建链，可整体迁到 shadcn。
5. **登录页无"记住我/忘记密码"**：与改版无关，属于原有功能范围。
